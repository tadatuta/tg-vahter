# Аудит VahterBot

Дата аудита: 7 августа 2026 года.

## Область проверки

Проверены архитектура, Telegram update pipeline, SQLite, конфигурация, безопасность,
наблюдаемость, тесты, CI и существующий пакет деплоя. Локально были успешно запущены
ESLint, TypeScript и 43 исходных теста. Production-зависимости на момент аудита не
содержали известных уязвимостей; в dev dependency tree было найдено шесть уязвимостей.

## Критические находки

1. SQLite работала в WAL-режиме поверх примонтированного Object Storage. WAL требует
   корректных файловых блокировок и shared memory, которых FUSE-монтирование GeeseFS
   не предоставляет. Это создавало риск потери и повреждения данных.
2. Публичный webhook Cloud Function не проверял Telegram secret token. Поддельный
   update мог инициировать реальные действия бота.
3. Одно чистое сообщение, включая нетекстовое, давало пользователю бессрочное доверие.
   Последующие сообщения не проверялись.
4. `edited_message`, скрытые `text_link.url`, `caption_entities`, медиагруппы и
   `sender_chat` не имели согласованной политики обработки.
5. Повторный вход не сбрасывал доверие неявно, но join-события обрабатывались без
   проверки перехода old status → new status и создавали несогласованное состояние.
6. Таблица `spammers` заполнялась, но не использовалась для последующей глобальной
   блокировки.
7. DB-admin был глобальным и мог влиять на все чаты. Это не соответствовало выбранной
   модели локального администрирования.
8. Связанные изменения SQLite не были объединены транзакциями; отсутствовали версия
   схемы и дедупликация `update_id`.
9. Невалидный regex приводил к fail-open, а пустой `SPAM_REGEX` работал не так, как
   описывала документация.
10. Не было graceful shutdown: процесс не вызывал `bot.stop`, checkpoint, закрытие БД
    и flush логов по SIGTERM.
11. Сборка не была воспроизводимой: файл regex не отслеживался Git, а старый ZIP
    сохранял удалённые файлы, в том числе `banDiagnostics.js`.
12. Отсутствовали Dockerfile, Compose, healthcheck, ограничения контейнера и runbook
    миграции.

## Дополнительные риски

- `message_log` и логи не имели retention policy.
- Telegram IDs валидировались только через `Number`/`isNaN`.
- В контейнере планировался одновременно stdout и неограниченный файловый лог.
- Не было алертов на невозможность ban/delete и потерю связи.
- Тесты подтверждали проблемное поведение как ожидаемое и не проверяли edits,
  entities, rejoin, локальные права, duplicate updates и shutdown.
- Большой regex не имел размеченного spam/ham-корпуса и метрик качества.

## Результат принятого remediation

Рабочая SQLite перенесена на локальный Docker volume, webhook удалён из runtime,
добавлен long polling, новая мигрируемая схема, две probation-проверки, глобальные
blacklist/spammers, локальные администраторы, обязательный API reverse proxy, graceful shutdown,
контейнерный security baseline, healthcheck и расширенный набор тестов.

AI-классификатор и содержательная оптимизация regex намеренно исключены из этого
релиза и будут проектироваться отдельно.
