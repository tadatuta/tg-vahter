# Принятые архитектурные решения

## Антиспам

1. Для пары `(chat_id, user_id)` проверяются первые два содержательных сообщения.
2. Содержательными считаются `text`, `caption` и скрытые URL из entities.
3. Нетекстовые сообщения не проверяются, не увеличивают счётчик и не дают доверие.
4. После двух чистых сообщений доверие сохраняется бессрочно, включая выход и rejoin.
5. Редактирование одного из двух probation-сообщений проверяется повторно.
6. Сообщения `sender_chat` пропускаются.
7. После получения доверия новые сообщения не проверяются. Это сознательное
   продуктовое ограничение.
8. Встроенные эвристики и regex могут автоматически добавить пользователя в
   глобальный список spammers и забанить в текущем чате.

## Полномочия

- Blacklist и spammers глобальны для всех пяти чатов.
- `SUPER_ADMIN_IDS` — глобальные владельцы бота.
- Telegram chat administrators и записи `chat_admins` действуют только в текущем чате.
- Локальный администратор может добавить пользователя в глобальный blacklist, но не
  может управлять администраторами или настройками другого чата.
- `/unspam` удаляет глобальную запись, но выполняет Telegram unban только в текущем
  чате.
- Legacy-таблица глобальных DB-admin не раздаёт права автоматически; новые локальные
  права назначаются явно.

## Runtime и инфраструктура

- Один контейнер, один процесс и одно SQLite-соединение.
- Long polling вместо webhook.
- Node.js 24 LTS, Debian Bookworm slim внутри контейнера.
- Ubuntu 26.04 LTS на Yandex Compute Cloud.
- Базовая VM: 2 vCPU 20%, 2 GB RAM, network SSD 10–20 GB.
- SQLite хранится только в локальном named volume `/data`.
- Telegram API доступен через обязательный HTTP(S)-proxy без авторизации.
- При недоступности proxy применяются backoff/restart и локальное логирование.
- Логи — JSON в stdout/stderr с Docker rotation.
- Операционные алерты отправляются в отдельный Telegram-чат.
- Secrets передаются через `.env` на VM с правами `0600` и не входят в image/Git.
- Деплой выполняется вручную через Docker Compose.

## Данные и backup

- Автоматического retention для message log нет.
- Регулярные backups и Object Storage не используются по решению владельца.
- Потеря VM/диска или повреждение файловой системы означает необратимую потерю данных.
- Для migration cutover допускается одноразовый rollback snapshot, который можно
  удалить после приёмки.

## Отложенный второй релиз

OpenAI-совместимый классификатор будет добавлен отдельно. Предварительно принято:

- вызывать его только после остальных эвристик;
- при недоступности продолжать работу по доступным эвристикам;
- не банить автоматически;
- отправлять решение на ручную модерацию в отдельный Telegram-чат.
