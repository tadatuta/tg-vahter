# Ручное тестирование VahterBot

## 1. Цель

Этот документ описывает полный ручной прогон бизнес-логики бота:
- обработка новых участников;
- проверка первого сообщения по эвристикам;
- бан/удаление сообщений;
- работа черного списка;
- админ-команды `/ban`, `/unban`, `/addadmin`, `/status`;
- проверка прав и отказоустойчивости.

## 2. Что нужно заранее

1. Telegram-аккаунт владельца теста (далее `A`), который будет супер-админом бота.
2. Минимум 2 дополнительных Telegram-аккаунта для проверок:
- `B` — обычный пользователь;
- `C` — пользователь для спам-сценариев.
3. Установленные локально:
- Node.js 22+;
- npm;
- sqlite3 CLI (желательно, для проверки БД).

## 3. Подготовка бота в Telegram (BotFather)

1. Откройте [@BotFather](https://t.me/BotFather).
2. Выполните `/newbot`, создайте нового бота, сохраните `BOT_TOKEN`.
3. Включите возможность добавления в группы:
- команда `/setjoingroups`;
- выберите бота;
- установите `Enable`.
4. Отключите privacy mode (критично для антиспама):
- команда `/setprivacy`;
- выберите бота;
- установите `Disable`.
5. (Опционально) задайте команды через `/setcommands`:
- `ban - ban user`
- `unban - unban user`
- `addadmin - add bot admin`
- `status - bot stats`

## 4. Получение Telegram user_id для админов

1. Узнайте `user_id` аккаунта `A` (например, через [@userinfobot](https://t.me/userinfobot)).
2. Запишите этот id — он пойдет в `ADMIN_IDS`.

## 5. Подготовка тестового чата

1. Создайте отдельную тестовую группу (лучше сразу supergroup).
2. Добавьте в нее аккаунты `A`, `B`, `C`.
3. Добавьте бота в эту группу.
4. Назначьте бота администратором и выдайте права:
- `Delete messages` (удалять сообщения);
- `Ban users` / `Restrict members` (банить пользователей).
5. Убедитесь, что бот видит все сообщения (privacy mode отключен в BotFather).

## 6. Подготовка проекта локально

1. В корне проекта:

```bash
cd /Users/tadatuta/projects/tg-antispam-bot
npm ci
cp .env.example .env
```

2. Заполните `.env` (пример):

```env
BOT_TOKEN=<TOKEN_ОТ_BOTFATHER>
ADMIN_IDS=<user_id_аккаунта_A>
SPAM_REGEX=(spam|http[s]?://|t\.me/|crypto|ставк|казино)
DB_PATH=/tmp/vahter.db
LOG_FILE=/tmp/vahter.log
```

3. Перед каждым полным циклом теста очищайте данные:

```bash
rm -f /tmp/vahter.db /tmp/vahter.log
```

## 7. Запуск бота

1. Запустите:

```bash
npm run dev
```

2. Ожидаемо в консоли:
- `Running in local development (long polling) mode`
- `Bot @<username> started in polling mode`

3. Держите отдельное окно терминала для логов:

```bash
tail -f /tmp/vahter.log
```

## 8. Ручные тест-кейсы (пошагово)

## TC-01: Проверка команды `/status` супер-админом

1. От аккаунта `A` отправьте в тестовый чат `/status`.
2. Ожидаемо:
- бот отвечает сообщением со статистикой;
- в ответе есть строки про новых пользователей, спамеров и черный список.

## TC-02: Новый участник + чистое первое сообщение

1. Если `B` уже в чате — удалите его и добавьте снова.
2. `B` вступает в чат.
3. `B` отправляет первое сообщение без триггеров regex (например: `всем привет`).
4. Ожидаемо:
- бана нет;
- сообщение остается в чате;
- пользователь удаляется из `new_users`;
- текст попадает в `message_log`.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM new_users WHERE user_id=<ID_B>;"
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM message_log WHERE user_id=<ID_B>;"
```

Ожидаемо: `0` в `new_users`, и `>=1` в `message_log`.

## TC-03: Новый участник + спам в первом сообщении

1. Удалите `C` из чата (если уже состоит), затем добавьте заново.
2. `C` отправляет первое сообщение, подходящее под `SPAM_REGEX` (например: `crypto spam t.me/test`).
3. Ожидаемо:
- бот банит `C`;
- сообщение `C` удаляется;
- `C` появляется в `spammers`;
- `C` удаляется из `new_users`.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM spammers WHERE user_id=<ID_C>;"
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM new_users WHERE user_id=<ID_C>;"
```

Ожидаемо: `1` в `spammers`, `0` в `new_users`.

## TC-04: `/ban` по reply

1. Пусть `B` отправит любое сообщение в чат.
2. `A` отвечает на это сообщение командой `/ban`.
3. Ожидаемо:
- `B` добавлен в `blacklist`;
- бот пытается забанить `B` в текущем чате;
- приходит подтверждение в чат.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT user_id, reason FROM blacklist WHERE user_id=<ID_B>;"
```

## TC-05: `/ban <user_id> [reason]`

1. От `A` отправьте `/ban <ID_C> manual test ban`.
2. Ожидаемо:
- в `blacklist` запись с reason `manual test ban`;
- бот отвечает подтверждением.

## TC-06: Черный список блокирует сообщение сразу

1. Пользователь, уже находящийся в `blacklist` (например `C`), отправляет сообщение в чат.
2. Ожидаемо:
- бот сразу банит и удаляет это сообщение;
- доп. эвристики не требуются.

## TC-07: `/unban <user_id>`

1. От `A` отправьте `/unban <ID_C>`.
2. Ожидаемо:
- запись из `blacklist` удалена;
- приходит подтверждение.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM blacklist WHERE user_id=<ID_C>;"
```

Ожидаемо: `0`.

## TC-08: `/unban` с невалидным id

1. От `A` отправьте `/unban abc`.
2. Ожидаемо:
- бот отвечает `Некорректный user_id.`

## TC-09: `/addadmin` доступна только супер-админу

1. От не-супер-админа (`B`) отправьте `/addadmin <ID_B>`.
2. Ожидаемо:
- команда игнорируется (без добавления в `admins`).
3. От `A` отправьте `/addadmin <ID_B>`.
4. Ожидаемо:
- `B` добавлен в таблицу `admins`;
- приходит подтверждение.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT COUNT(*) FROM admins WHERE user_id=<ID_B>;"
```

Ожидаемо: `1` после шага 3.

## TC-10: `/status` для разных типов авторизации

1. Супер-админ (`A`) вызывает `/status` -> должен получить ответ.
2. Добавленный через `/addadmin` пользователь (`B`) вызывает `/status` -> должен получить ответ.
3. Любой пользователь без прав вызывает `/status` -> ответа быть не должно.

## TC-11: Спам в `caption`

1. Удалите и снова добавьте `B` в чат.
2. `B` отправляет фото/видео с подписью, содержащей spam regex.
3. Ожидаемо:
- подпись проверяется как текст сообщения;
- пользователь банится как спамер.

## TC-12: Сообщение без текста/подписи

1. Удалите и снова добавьте `B`.
2. `B` отправляет стикер (без текста и подписи).
3. Ожидаемо:
- это считается чистым первым сообщением;
- пользователь удаляется из `new_users`;
- в `message_log` пишется `NULL` в `message_text`.

Проверка БД:

```bash
sqlite3 /tmp/vahter.db "SELECT message_text FROM message_log WHERE user_id=<ID_B> ORDER BY id DESC LIMIT 1;"
```

Ожидаемо: пустое значение (`NULL`).

## TC-13: Устойчивость к отсутствию прав бота

1. В правах администратора бота временно снимите:
- `Delete messages`;
- `Ban users`.
2. Повторите спам-кейс (`TC-03`).
3. Ожидаемо:
- бот не падает;
- в логах есть ошибки про невозможность ban/delete;
- процесс продолжает работать.
4. Верните права обратно после проверки.

## TC-14: Отключенные эвристики (пустой `SPAM_REGEX`)

1. Остановите бота.
2. В `.env` установите `SPAM_REGEX=` (пусто).
3. Очистите БД, запустите снова.
4. Новый пользователь отправляет очевидный спам.
5. Ожидаемо:
- бана по эвристикам нет;
- в логах предупреждение про отключенные эвристики.

## TC-15: Невалидный `SPAM_REGEX`

1. Остановите бота.
2. Установите `SPAM_REGEX=[`.
3. Запустите снова.
4. Ожидаемо:
- бот стартует;
- в логах ошибка `Invalid SPAM_REGEX ... heuristic checks disabled`;
- `isSpam` фактически отключен.

## TC-16: Сохранение состояния после рестарта

1. Выполните несколько действий, чтобы заполнить БД (например, `spammers` и `blacklist`).
2. Остановите бота (`Ctrl+C`).
3. Запустите снова `npm run dev` (не удаляя `/tmp/vahter.db`).
4. Вызовите `/status`.
5. Ожидаемо:
- статистика сохраняется между перезапусками.

## TC-17: Комментарии к каналу (если используете этот сценарий)

1. Создайте канал и привяжите к нему обсуждение (discussion group).
2. Добавьте бота в discussion group и выдайте права как в разделе 5.
3. Пишите комментарии от новых пользователей в обсуждении.
4. Ожидаемо:
- логика работает так же, как в обычной группе.

## 9. Полезные SQL-команды для быстрой диагностики

```bash
sqlite3 /tmp/vahter.db "SELECT * FROM new_users;"
sqlite3 /tmp/vahter.db "SELECT * FROM spammers;"
sqlite3 /tmp/vahter.db "SELECT * FROM blacklist;"
sqlite3 /tmp/vahter.db "SELECT * FROM admins;"
sqlite3 /tmp/vahter.db "SELECT id,user_id,chat_id,message_text,logged_at FROM message_log ORDER BY id DESC LIMIT 20;"
```

## 10. Что прикладывать к баг-репорту

Для каждого дефекта фиксируйте:
1. Название кейса (например, `TC-03`).
2. Фактическое поведение.
3. Ожидаемое поведение.
4. Скриншоты чата.
5. Фрагмент логов из `/tmp/vahter.log`.
6. SQL-снимок состояния таблиц (`new_users`, `spammers`, `blacklist`, `message_log`).

## 11. Завершение теста и очистка

1. Очистите тестовую БД/логи:

```bash
rm -f /tmp/vahter.db /tmp/vahter.log
```

2. Удалите тестового бота из боевых чатов (если случайно добавляли не в тестовый).
3. Проверьте, что в `.env` не осталось боевых токенов перед коммитами/публикацией.
